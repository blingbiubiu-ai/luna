# Worker Model Providers

Model providers are optional Agent-scoped plugin contributions, independent of operation dispatch.
The manifest declares `workerModelProviders` with a unique provider ID, display name, release-relative
entrypoint and `responses` protocol. The Service loads the ordinary lightweight `plugin.js`; the Worker
loads the model adapter in a Bun child process. Core contains no provider-specific endpoints or SSO code.

## Installation and accounts

Platform installation still uses immutable marketplace releases and Service restart. Agent enablement
still uses `AgentPluginStore` ownership and revision checks. The authenticated Service management API
under `/api/model-providers` requires an explicit Agent; owners choose an assigned, online Worker that
advertises `worker-model-provider-v1`. Disabled, paused, unsupported or unauthorized bindings fail.

Service transfers release assets and canonical checksums over the private Worker RPC. Worker verifies
digest, manifest identity, listed assets, path containment and absence of symlinks before caching code
under `<worker-data>/plugins/releases/<plugin>/<digest>`. It never downloads dependencies at startup.

Credential import is bounded, validated by the adapter, CAS-protected and idempotent by request ID.
Only a successful import changes the current account pointer. Worker SQLite stores AES-GCM ciphertext
and immutable credential revisions; AAD binds Worker, Agent, plugin, provider, account and revision.
The Worker-local key is `<worker-data>/model-provider-secrets/master.key` with mode 0600. Service stores
only summaries in `agent_model_provider_accounts`, including model catalog and revision references.
Credentials cross Service memory during import but are not persisted there or returned to Dashboard.
Old credential revisions remain available for pinned executions; basic version has no garbage collector.

## Profile and placement

Profile revisions have nullable `model_provider_json`. A Worker model reference contains plugin/provider,
Worker, account, credential revision and release digest. It is part of configuration and provider
fingerprints, durable invocation configuration, preparation input and hashed Job input. Ephemeral keys
and child ports are excluded. Existing ordinary Profiles remain compatible. Plugin Profiles require
Codex and cannot combine a manual gateway URL/Key; transitions explicitly clear a retained Key.

Preparation restricts candidates to the binding Worker and rejects an existing conflicting context or
explicit Shadow Worker. Provider Profiles have no cross-Worker failover. Source identity is rechecked
against prepared input during Job assignment and against accepted Job bindings during credential
delivery. Changes to current account/Profile do not rewrite previous revisions or in-flight Jobs.

## Execution and API

The Worker owns a model listener separate from control and Executor callback listeners. Its default
port is the control port plus 200; `modelPort`/`modelHost` can configure it. Containers connect through
`host.docker.internal`, including the existing Linux host-gateway mapping. Public model routes are only
`GET /v1/models` and `POST /v1/responses`, requiring a purpose-scoped key.

Both reverse and direct Workers proxy plugin Jobs' private Executor calls through the Worker. Model
and source are frozen in the hashed Job; Worker records them with the assignment. Before forwarding
private Credentials it verifies that binding and supplies `CODEX_PROVIDER_MODE=gateway`, model base
URL and an execution-scoped Key. Upstream credentials never enter the Runner. Worker grant records
contain only Key hashes and scope bindings. Stable HMAC-derived keys use a Worker-local secret, and
credential renewal extends the same grant. Expiration, current reservation/assignment, connectivity,
model and account are checked on requests and stream pulls. Test grants live only for one validation.

Each Agent/provider/release uses an isolated child with private HOME, minimal environment, private
loopback API and bounded startup. Keys/credentials are not placed in argv; initialization uses stdin.
Provider stdout is drained and stderr is discarded. This is trusted code with process isolation,
not an OS security sandbox. A crash fails the current request; a later request can rebuild the child.

Responses forward with backpressure and cancellation, preserve SSE and use an Agent/context session
identity generated by Worker. There is one concurrent model request per Agent; busy returns 429.
Client authorization and arbitrary client headers do not go to the provider. Job completion, plugin
disable and shutdown revoke grants; reservation changes and Service disconnection deny new requests.
Worker shutdown closes the listener, aborts in-flight requests and stops children.

## Dashboard and validation

The Model Configuration page and Agent plugin pages share Worker catalog/account controllers with
browser authorization, masked account summary, expiration, catalog refresh and API protocol/addresses.
Plugin details use an account workspace; model configuration uses a saved-model workspace,
Provider directory and two-step model picker, all backed by the same generic management APIs.
The platform Plugins page links to the owner's Agent model configuration. A disabled provider can
be enabled by the explicit sign-in action. File import remains a fallback under a disclosure.
"Add from Provider" opens a Codex Profile editor that selects an enabled provider/account/model,
automatically inheriting the Worker/source reference and omitting manual API/secret fields.
Query keys and component identities include Agent/provider/Worker scope.

Providers may declare an OAuth login contribution and implement the optional adapter login contract.
Service creates a ten-minute, owner/Agent/Worker/provider/config-revision-bound login flow and
transfers the installed release before asking Worker to start it. The adapter creates its own
loopback credential receiver and SSO state; its authorization URL redirects to Service's
plugin-declared `login.callbackPath` callback with a `flowId` query parameter. Omitted paths
use `/api/model-providers/login/callback`. Core registers literal callback paths from the installed
plugin manifests; it has no TRAE-specific route. Paths cannot claim built-in API, authentication
or Dashboard namespaces. The selected path is frozen into the login flow and checked before relay.
The TRAE plugin declares `/authorize`, which its upstream authorization page requires; using an
API route instead is rejected upstream with a misleading CN eligibility error.
The authenticated callback relays bounded parameters to that receiver over the private management
channel. The TRAE adapter only forwards its whitelisted fields to its own 127.0.0.1 receiver, where
the original SSO state and CN account checks run. Browser and Worker need not share a machine.
Callbacks redirect to a URL without credentials and use no-store/no-referrer headers.

Dashboard polls the owner-bound flow. On success Worker validates the credential/catalog, performs
the existing CAS/idempotent encrypted account import and discards the temporary login credential.
Service receives only the account summary and rechecks ownership/config before persisting metadata.
Disable/cancel/timeout invalidates the flow; login flows are ephemeral and do not survive Service restart.
The protocol/API information uses the existing Worker Responses listener; Luna still injects an
execution-scoped Key, and showing an address does not create a public unauthenticated gateway.

Plugin Profile connection tests run the actual Codex CLI in a one-shot container on the binding
Worker with the Worker runtime mounted read-only and a validation-scoped Key. Success requires the
expected reply. Ordinary Profiles retain the existing Service-side tester. Ownership/source are
rechecked after asynchronous testing and before activation; failed tests cannot activate.

The initial external adapter is `trae-provider` / `trae-code-cn`, pinned to Magpie plugins 0.3.7.
Version 0.2.4 implements Dashboard browser SSO and retains its independent local SSO/export helper.
Only OpenAI Responses text, streaming, client tools and reasoning history are supported. No account
rotation, automatic credential renewal, Anthropic compatibility or public multi-tenant gateway is added.

Worker plugin grants set `CODEX_WEB_SEARCH_MODE=disabled`. Both stdio and PTY Codex adapters
apply `web_search="disabled"`, because the basic Worker contract provides client tools rather
than OpenAI-hosted web search. Ordinary gateway Profiles retain their existing search settings.
The TRAE adapter accepts function/custom tools and namespace groups containing those tools;
its upstream library preserves the namespace when converting calls back to Responses events.

The TRAE wrapper reuses the upstream auth loader per credential digest, with a bounded cache in
the Agent/provider child. The loader owns upstream multi-turn `extra_info` state; different
credentials do not share it. Responses usage is forwarded unchanged, including cached input,
cache writes and reasoning counts. The Worker preserves bounded `Retry-After` headers, while
other upstream response headers remain filtered. Provider request usage is not yet persisted
as Luna task-level token accounting; clients still receive the full Responses usage.
