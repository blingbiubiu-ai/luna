# Artifacts

## Goal

Artifacts are Luna's durable resource protocol. Any file-like resource that crosses a process, sandbox, HTTP, persisted-data, Dashboard, or channel boundary should be represented as an artifact instead of a host-local path.

Artifacts give Luna one resource model for inbound attachments, diagnosis dumps, runner-generated reports, Dashboard previews, Feishu links, and sandboxed runner materialization.

## Artifact Identity

`artifact:<id>` is the only file reference that crosses process, sandbox, HTTP,
persisted-data, Dashboard, or channel seams. It is safe to persist in messages,
timeline entries, task results, prompts, and reports.

Older structured message content remains available through the generic session
timeline. Readers do not recover it through a filesystem attachment path or a
specialized attachment query.

Presentation and access forms are generated by Service:

- `/api/artifacts/:id/content?expires=...&sig=...` returns raw original content.
- `/artifacts/:id/preview?expires=...&sig=...` opens the user-facing preview page.
- `/api/artifacts/:id/preview?expires=...&sig=...` returns preview data for the web client.

The frontend and runners never compute signatures. They receive artifact refs or Service-generated URLs.

## Storage Model

`managed_artifacts` is the durable catalog. It records:

- artifact id.
- scope type and scope id, such as session or task.
- related user id when the artifact is associated with a human user interaction.
- producer, kind, display name, MIME type, size, and hash.
- storage backend and Service-private storage key.
- status, retention policy, retention expiry, creation time, and deletion time.

The storage key is a Service-private fact. It must not be written into chat messages, runner-visible durable records, Dashboard DTOs, or Feishu replies.

## Registration Flow

Artifacts enter the system through the same registry path:

- inbound channel attachments are downloaded and registered before or during message persistence.
- diagnosis outputs are registered as artifacts rather than served through custom routes.
- Main Runner outputs that reference user-visible generated files should use `luna artifacts register`.
- Work Runner outputs that reference user-visible generated files should use `luna artifacts register`.
- Task Runner outputs that reference user-visible generated files must use `luna artifacts register`.

Service also applies one shared output-finalization seam to Main action
payloads and Task results. Work terminal output is diagnostic only; Work must
register files before sending artifact references through message commands. `artifactizeRunnerOutputValue`
recursively replaces eligible runner-workspace paths with registered
`artifact:<id>` references, infers the content kind and MIME type, and records
the correct session or task scope. This is a safety net for provider output;
explicit runner registration remains the preferred protocol. Inbound
channel/local-file normalization is a separate seam because those files do
not originate in a runner workspace.

Runner registration uses content upload to Service. Service validates runner scope:

- Main Runner registers only to its session scope.
- Work Runner registers only to its session scope.
- Task Runner registers only to its task scope.
- runner tokens cannot spoof arbitrary session/task ownership.

## Access Flow

Content access uses both signed links and authenticated authorization:

- A valid signed URL is a bearer operation until expiry.
- Signed link expiry is 2 hours.
- After expiry, anonymous access fails.
- Authenticated related users can still access artifacts related to them.
- Runner bearer tokens can read artifact ids granted to that exact token. They
  can also read any artifact whose `related_user_id` matches the token actor;
  this permits plugins to create same-owner artifacts without requiring a
  separate grant. Cross-user access remains denied.
- Runner tokens receive initial launch grants, gain page-specific grants for
  artifact refs returned by an authorized generic timeline read, and gain a
  grant for content they successfully register in their own runner scope.
- Internal service callers can perform service-owned operations.

Knowing an artifact id is not enough to read content.

```mermaid
flowchart LR
  Runner[Runner or channel adapter] --> Register[POST /api/artifacts]
  Register --> Store[managed artifact storage]
  Store --> Ref[artifact:id]
  Ref --> Preview[/artifacts/:id/preview signed link]
  Ref --> Content[/api/artifacts/:id/content signed link]
  Preview --> PreviewData[/api/artifacts/:id/preview data]
```

## Preview Flow

Preview is split between web UI and API:

- `/artifacts/:id/preview` is a web route. It loads the Dashboard preview application.
- `/api/artifacts/:id/preview` is a JSON API. It validates the same `expires/sig` pair or authenticated access, then returns metadata, render mode, optional text content, and `downloadUrl`.
- `/api/artifacts/:id/content` returns original bytes/text and does not render UI.

Render modes include markdown, html, json, text, image, pdf, and binary. Browser-previewable content should use inline disposition where supported; opaque binary content should be downloaded or opened as original content.

## Markdown And HTML Internal References

Preview data can project nested artifact references:

- Markdown image refs such as `![image](artifact:imageId)` become signed content URLs.
- Markdown links such as `[report](artifact:fileId)` become signed preview URLs.
- Inline code or bare `artifact:fileId` references can become preview links.
- HTML-like `src="artifact:imageId"` becomes a signed content URL.
- HTML-like `href="artifact:fileId"` becomes a signed preview URL.

Projection is allowed only when the referenced artifact is reachable from the source artifact:

- same artifact id, or
- same scope type and scope id, or
- same non-null related user id.

References that fail the reachability check remain literal `artifact:<id>` text.

## Runner Protocol

Runner input should keep artifact references intact. When a runner needs bytes, it materializes the artifact:

```bash
luna artifacts materialize artifact:<id>
```

Generic timeline reads grant only refs present in the returned page after
cursor, limit, and reference filtering. Reading a session never grants every
artifact in that session or task.

When a runner creates a user-visible file, it registers the file:

```bash
luna artifacts register workspace/final-report.md --json
```

The runner should then mention `artifact:<id>` or use Service-generated preview/content links. It should not expose raw `workspace/...`, `attachments/...`, or host absolute paths to users.

## Non-Goals

- Do not use legacy path-based file routes.
- Do not expose raw workspace paths as durable user links.
- Do not depend on compatibility with old task/session records.
- Do not introduce diagnosis-specific file serving.
- Do not introduce a separate artifact token system.

## Remote Runner output

Remote Runners use the same content-upload `luna artifacts register` and download/materialize APIs. For contexts prepared on a remote Worker, Service never resolves output paths against its own filesystem. The legacy output fallback replaces unregistered file-path references with an explicit upload-required notice; it cannot publish a remote file by reading a same-named local path. Registered `artifact:id` references retain existing access and delivery behavior.
